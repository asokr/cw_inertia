# Ozon A/B-тестирование

## Права доступа

- Permission: `subscriber oz ab testing`
- Middleware панели: `auth`, `verified`, `panel.access`, `wb.cabinets.migrated`, `permission:subscriber oz ab testing`

## Назначение

Инструмент для A/B-тестирования **главной фотографии** карточки товара Ozon. По сценарию как у [WB A/B](wb-ab-testing.md): товар → эксперимент → рекламная кампания → варианты фото → циклы → победитель.

Кабинет Ozon — единый ([oz-cabinets.md](oz-cabinets.md)). Workspace: `/panel/oz/ab-testing`.

Для работы с рекламой нужны ключи **Performance API** (`performance_client_id` + `performance_client_secret` в кабинете). Seller API-ключ рекламу не открывает.

`client_id` в запросе токена всегда в формате `digits@advertising.performance.ozon.ru` (пользователь может вставить только цифры или полный id — суффикс добавляется в `OzonPerformanceApiService::normalizeClientId`).

Ошибки при загрузке кампаний:

| Ситуация                                        | Сообщение пользователю                                                            |
| ----------------------------------------------- | --------------------------------------------------------------------------------- |
| Ключей нет                                      | «Укажите ключи рекламы Performance API в кабинете Ozon.»                          |
| Ключи есть, Ozon ответил 401 / `invalid_client` | «Неверные данные для подключения»                                                 |
| Ключи есть, другая ошибка токена                | «Не удалось подключиться к рекламе Ozon. Проверьте данные для подключения.»       |
| 429 / «лимит активных запросов (максимум 1)»    | «Ozon сейчас не принимает запросы. Подождите несколько секунд и обновите список.» |

Performance API пускает **один активный запрос** на аккаунт. Клиент сериализует вызовы lock'ом (`Cache::lock` на client_id), держит паузу ≥ 1 с между запросами и до 3 раз повторяет 429 (1 с / 2 с / 4 с). Список кампаний для эксперимента **не** дергает `GET .../campaign/{id}/objects` на каждую РК — только payload списка.

### Scope (MVP)

- Товары → эксперименты товара → workspace
- Одновременно `running` — не больше одного на товар и не больше одного на кампанию
- Фото: 2–6, JPEG/PNG, **public disk** (Ozon принимает только публичные URL)
- Цикл: минимум и по умолчанию **30 минут** (или раньше, если набраны показы за круг) — смена фото
- Статистика эксперимента — **дельта** относительно снимка на старте круга (тик ~60 с; API может отставать от кабинета)
- Показы: **один sync-запрос на кабинет** раз в ~60 секунд (`ProcessOzAbCabinetTickJob`). В запрос входят все running-кампании кабинета (до 10 id). Новый эксперимент не поднимает отдельную цепочку — попадает в уже идущий тик.
- Fallback-тик раз в 2 минуты, если цепочка job оборвалась.
- Движок: queue `oz_ab_testing` + fallback `subscriber:oz-ab-testing-tick`
- Экран, пока эксперимент «В процессе», сразу запрашивает свежий `selectedExperiment` и дальше каждые 5 секунд. Кнопка запуска отвечает отдельно и сама опрос не включает: его включает статус «В процессе» уже на экране. Перезагрузка страницы читает те же суммы кругов из базы.

## Реклама (Performance API)

Документация: https://docs.ozon.ru/api/performance/  
Host: `https://api-performance.ozon.ru`

Показываем кампании `advObjectType = SKU` в статусах `CAMPAIGN_STATE_RUNNING` и `CAMPAIGN_STATE_INACTIVE`.  
Не показываем баннеры, видеобаннеры, оплату за заказ, архив и модерацию.

В UI у списка кампаний — иконка-подсказка (тултип): какие кампании подходят, без технических названий полей API.
Выбор кампании подтверждается модалкой в UI («Использовать кампанию?») с кнопками «Да/Нет» и состоянием «Присоединение…» во время запроса.

Создание: `POST /api/client/campaign/cpc/v2/product` с `placement = PLACEMENT_SEARCH_AND_CATEGORY` и `productAutopilotStrategy = TARGET_BIDS`. Параметр `productCampaignMode` из запроса убран (Ozon удалил его в октябре 2024; без `placement` API отвечает «Недопустимое значение типа продвижения»).  
Добавление товара: `POST /api/client/campaign/{id}/products` (только add) для существующих кампаний. Для добавления отправляем `bids` с `sku` (без передачи ставки из настроек эксперимента). При выборе существующей кампании, где уже есть другие товары, UI запрашивает подтверждение замены текущего состава на SKU эксперимента; после подтверждения prepare удаляет чужие SKU (`POST .../products/delete`) и добавляет SKU эксперимента. При создании новой кампании SKU передаётся сразу в `create` payload. При выборе существующей инструмент добавляет текущий SKU и проверяет, что он появился в кампании до запуска.  
Старт/стоп: `activate` / `deactivate`. Если на старте SKU не найден в привязанной кампании, инструмент делает авто-попытку добавить SKU и продолжить запуск.

Статистика (тик кабинета ~60 сек): один `POST /api/client/statistics/products/sku` на кабинет, `campaignIds` = все running-кампании (пачки по 10). API отдаёт строки по SKU **и дате** (окно не раньше вчера). Снимок цикла — сумма дат `>=` дня старта цикла (МСК), без вчерашней истории кампании. Если в ответе одна SKU на кампанию, её берём даже при расхождении идентификатора; если SKU несколько и нужной нет — нули не затирают уже накопленный `views_end`.

Baseline первого круга — ноль. На экране сумма дат с дня старта цикла (МСК): вчерашняя история кампании не входит. Следующий круг вычитает снимок на момент смены фото. Пока кадр на карточке не подтверждён, круг не сменяется, но эта сумма уже видна.

Пополнение рекламного счёта из инструмента **нет**: в Performance API нет перевода денег на кампанию (аналога WB `budget/deposit`). `dailyBudget` помечен deprecated; `weeklyBudget` — это лимит расхода, не пополнение. Создаём CPC-кампанию (`POST /api/client/campaign/cpc/v2/product`: название, дата, товар). Перед запуском проверяйте ставку и остальные параметры кампании в кабинете Ozon. Деньги списываются с рекламного счёта Ozon, пополнить его можно только в кабинете Ozon.

## Товары (Seller API)

Синхронизация: `POST /v3/product/list` + `POST /v3/product/info/list`.

В `product/info/list` поле `primary_image` приходит **массивом URL**, не строкой. Синк берёт первый URL (то же для `images`). SKU — из `sources[]`, иначе `sku` / `fbs_sku` / `fbo_sku`.

Каждый размер на Ozon — отдельный `product_id`. В списке A/B показываем **товар**, SKU свёрнуты: клик по карточке раскрывает размеры, клик по SKU открывает эксперименты. Группировка: `model_info.model_id`, иначе название. Пагинация — 25 товаров на страницу, не 25 SKU. Колонок бренда и цены нет — этих полей нет в этом запросе.

## Фото карточки (Seller API)

Загрузка фото — [POST /v2/product/pictures/import](https://docs.ozon.ru/api/seller/#operation/ProductImportPicturesV2). Метод затирает **весь** набор изображений и требует публичные URL (Ozon сам скачивает файл). Ссылка на `127.0.0.1` / localhost не принимается: запуск останавливается до запроса. Прежний `/v1/product/pictures/import` не используем.

Тело запроса — `items` из одного товара (метод принимает 1–100). Товар задаётся `offer_id` (артикул, 1–1000 символов). `product_id` в элемент не передаём. `primary_image` — строка с одной ссылкой на главное фото, не массив. В `images` — только остальные кадры снимка, не больше 29, без повтора главного. Поля товара в корне запроса Ozon отклоняет.

Перед стартом сохраняем `gallery_snapshot` (images, 360, цвет). Смена варианта = новое главное + остальные из снимка. На stop возвращаем исходную галерею; на complete ставим победителя.

**Фото №1 отправляется сразу при запуске**, до открытия цикла. На витрине оно появляется после модерации, поэтому несколько минут и даже часы со старым кадром ещё не значат, что запрос не прошёл. Следующий вариант уходит только после того, как текущий кадр подтверждён на карточке и прошёл свой круг.

Перезапуск с «Остановлен»: снова ставится **фото №1** (не вариант, на котором остановились) и открывается новый цикл. Если первое фото совпадает с исходным главным, на карточке Ozon визуально ничего не меняется до следующего круга.

Статус загрузки: `POST /v2/product/pictures/info`. Импорт асинхронный: ждём ~8 с, затем опрашиваем до ~32 с. Старт и смена проходят при `uploaded` (или URL без ошибок после паузы), даже если на карточке ещё прежнее главное: файл скачан, витрина обновится после модерации. `pending` / ошибка файла / таймаут — «Ozon не принял фотографию» / «не успел обработать». Ссылка на localhost до запроса не отправляется.

Пока круговой тик не узнает нужный кадр на карточке, таймер круга стоит и следующее фото не отправляется. Показы при этом уже считаются: это сумма статистики с дня старта цикла. Сверка каждый тик, даже если ссылка главного фото не менялась: сначала главное фото карточки товара, затем статус загрузки (он может ещё держать старый кадр). Свой файл читается с диска. Сравнение: MD5, а если Ozon пережал картинку — отпечаток. Совпадение пишет в журнал «На карточке нужное фото». Число на экране — сумма дат с дня запуска, без вчерашней истории кампании, поэтому оно меньше полного итога кабинета Ozon за два дня.

Полный след пишется в `storage/logs/oz-ab-photos-YYYY-MM-DD.log` (канал `oz_ab_photos`, без ключей API). Каждый тик: ответ статистики (кампании, даты, SKU, показы, ключи строки и что разобрали), снимок по датам с отброшенными днями до старта цикла, сверка кадра (ссылка карточки, свой файл с диска или скачивание, MD5, отпечаток, расстояние) и дельта круга, которую пишем на экран. В журнал эксперимента — одна строка ожидания и одна строка, когда фото на карточке совпало.

Цикл по умолчанию **30 минут** (или раньше, если набраны показы за круг) считается от подтверждения фото на карточке. Показы в инструменте — сумма с дня старта цикла, тик ~60 с. Performance API часто отстаёт от кабинета Ozon на десятки минут.

## Очередь

```
php artisan queue:work --queue=oz_ab_testing,default
```

Основной цикл: job сам ставит следующий тик через **60 секунд**.  
Fallback: `subscriber:oz-ab-testing-tick` каждые 2 минуты.
